【强制约束：修改后必须自检，避免以下错误】

一、通用（任何改动都要遵守）
1. 不要臆造不存在的类、方法、字段、Mapper 方法或配置项。修改前先检查：
   - 实体类字段与数据库列是否一致（下划线→驼峰）；
   - Mapper 接口是否已存在该方法，不存在则先补接口和 XML/注解；
   - Service/Controller 注入的 Bean 是否已定义。
2. 所有 Controller 方法必须返回项目统一的 Result 包装（如 Result.success/Result.error），不要直接返回实体或裸字符串，除非原方法已是该风格。
3. 新增/修改接口必须考虑：参数校验（@Valid / 手动判空）、异常捕获、事务边界（多表写操作加 @Transactional）。
4. 不要修改已经执行过的 Flyway 迁移脚本（db/migration 下已有版本号的文件），如需变更表结构，新增 V{日期}_x__xxx.sql，并使用幂等写法（IF NOT EXISTS / INSERT IGNORE / 先查后改）。
5. 数据库表名 `match` 是 MySQL 保留字，SQL 中必须写成 `` `match` ``，MyBatis-Plus 实体上加 @TableName("`match`") 或确保生成的 SQL 带反引号。
6. 时间字段统一用 LocalDateTime/LocalDate，JSON 序列化格式保持项目现有配置，不要混用 Date 和 LocalDateTime。
7. 不要引入新的第三方依赖，除非我明确要求；不要升级 Spring Boot / MyBatis-Plus / Flyway 版本。
8. 【前端只改外置目录】以后对前端页面的更改（HTML / CSS / JS / 图片 / favicon），一律只改工程根目录的 templates/、static/（即 @templates、@static）。不要改 src/main/resources/templates 或 src/main/resources/static——本地 Docker 挂载的是根目录这两处，改 classpath 里的副本刷新看不到。Java/配置/Flyway 仍改 src/。
9. 必须保证当前所有功能都可以正常使用。安全加固、抽组件、去冗余都不能改变已有业务结果、权限范围和页面行为。改完按改动面自检相关页面和接口；拿不准会不会影响现有功能时，保持原行为。
10. 新增或修改控件时，放在当前页面已有信息流里合适的位置：能加在现有控件上就不要另起一块。任何宽度下都不得撑破或溢出当前布局，信息要能看清，样式跟现有页面一致，安静、不抢主内容。
11. 已有服务、片段、样式和接口能复用就复用，不要为同一件事再写一套平行实现。
12. 【雪花 ID / Long 主键】本系统用户、赛事、场次等主键多为雪花 ID（约 19 位），超出 JavaScript Number 安全整数（2^53-1）。凡经浏览器 JSON/JS 处理的 ID（接口响应、data-*、拼 URL、本地比较）必须按字符串传递与使用：Jackson 可用 `@JsonSerialize(using = ToStringSerializer.class)` 或显式 `String.valueOf`；前端用 `String(id)` / 字符串比较，禁止依赖 JSON number。模板里 `th:href` 等服务端渲染路径不受此限，但若页面随后用 JS 重绘表格/链接，必须走字符串 ID，否则会精度丢失、查无用户并误跳转（如回首页）。改动涉及 ID 序列化或前端拼链时必须自检此项。
13. 【办赛人员】办赛人员包括：超级管理员（role=0）、普通管理员（role=1）、赛事主办用户（该届赛事的 hostUserId）。涉及权限、消息通知受众、管理入口时，须按此三类识别；勿把「仅参赛选手」与办赛人员混用同一套受众逻辑。
14. 【消息通知受众】同一届赛事内：环节汇总（报名开始/结束含报名结果、抽签开始/结束、抽签结果汇总、小组赛/单组完赛详细数据、各淘汰轮落败者积分、赛事结束全量积分等）发给全体办赛人员（含已参赛者）。个人向（分组结果、对阵、本人赛事积分、截止提醒等）只发给当事人；已参赛办赛人员另收本人个人向，未参赛办赛人员不收他人个人向私信。收件箱与详情均以收件关系为准，不得因管理员身份列出或打开全部已发布通知。

二、避免 500（服务端异常）
1. 所有可能为 null 的查询结果、集合、Optional 必须先判空再使用，禁止直接 .get(0) / .stream() / .equals()。
2. 字符串比较用 Objects.equals 或 "常量".equals(var)，禁止 var.equals("常量")。
3. 除法、取模、数组/集合下标访问前必须做边界与零值判断。
4. 日期解析、数字转换（Integer.parseInt 等）必须 try-catch 或使用安全工具方法。
5. 外键关联查询不要假设数据一定存在；关联对象为 null 时要有兜底展示。
6. 异步/定时任务中的异常必须捕获并记录日志，不能让异常冒泡导致线程池或调度器异常。
7. 任何新增的 @RequestMapping 路径不要与已有路径冲突（检查 Controller 中已有映射）。

三、避免 40x（客户端错误）
1. 路径变量/请求参数必须与前端调用完全一致（@PathVariable 名称、@RequestParam 名称、required 属性）。
2. POST/PUT 接口的 @RequestBody DTO 字段名必须与前端 JSON 字段名一致；如前端用驼峰，DTO 也用驼峰。
3. 需要登录/权限的接口，确认拦截器或 Spring Security 配置不会误拦；公开页面（如排行榜、导出）要显式放行。
4. 表单提交注意 CSRF（若启用了 Spring Security），Thymeleaf 表单中保留 th:action 自动注入的 CSRF hidden 字段，不要手写覆盖。
5. 静态资源路径使用项目现有写法（如 @{/css/xxx.css}），不要硬编码 /static/ 前缀。
6. 分页参数、枚举值、状态值要与后端枚举/常量定义一致，不要凭空写魔法值。

四、避免 Spring EL / 表达式错误
1. application.properties 中的 ${...} 只能引用已存在的配置项或环境变量；新增配置必须同时在 application.properties 中给出默认值或在 docker-compose 环境变量中声明。
2. @Value("${xxx}") 必须提供默认值（如 ${xxx:default}），避免启动时因缺失配置导致 500 或启动失败。
3. Thymeleaf 中的 ${...} 只能访问模型里真实存在的属性或已注册的 Bean（如 @beanName）；不要访问未放入 Model 的对象。
4. SpEL 中不要调用可能为 null 的对象方法；复杂表达式先在 Controller 中算好放入 Model，模板里只做简单展示。
5. 不要在 Thymeleaf 中写 Java 语法（如 new、强转、lambda），保持表达式简单。

五、避免 Thymeleaf 模板错误
1. 所有模板必须能被 Thymeleaf 解析：标签闭合、属性引号成对、th:* 属性拼写正确（th:text / th:each / th:if / th:href / th:action / th:object / th:field）。
2. th:each 的语法必须是 "item : ${list}" 或 "item, stat : ${list}"，不要漏掉冒号或 ${}。
3. th:if / th:unless 中的表达式不要以 HTML 实体形式出现；比较用 eq/ne/gt/lt 或 ==/!=，字符串常量加单引号。
4. 表单绑定（th:object + th:field）时，确保 Controller 放入了对应对象，且字段名与 DTO 一致。
5. 引用片段用 th:replace / th:insert / th:include 时，路径和片段名必须存在；片段参数传递语法正确。
6. 模板中引用的静态资源统一用 @{...}，不要写死相对路径。
7. 【前端唯一真相源】工程根目录 templates/、static/（@templates、@static）为前端权威目录（docker-compose 挂载到容器 /app/templates、/app/static；Thymeleaf/静态资源优先读外置路径）。改页面必须直接改这两个目录，禁止改 src/main/resources 下对应副本。
8. 新增模板/静态文件：只在根目录 templates/、static/ 创建即可生效。无挂载的生产镜像若仍打进 WAR，发布前再用根目录覆盖 src/main/resources，或保证发布环境同样挂载根目录；日常开发不要去改 classpath 副本。
9. 修改模板后提醒我：本地开发 spring.thymeleaf.cache=false 且已挂载外置目录时，浏览器 F5/强刷即可；纯 Java/配置/Flyway 改动才需要 ./gradlew build && docker-compose up --build -d。
10. 页面级 <style> / 额外 <link> 不要写在 th:replace="~{fragments :: head(...)}" 的 <head> 内部——整段 head 会被替换，样式不会出现在最终 HTML。应像赛事详情页一样把 <style> 放在 <body> 内（navbar 之后），或写入 static/css 再用 @{...} 引入。覆盖内联 style="display:none" 时需用 display: … !important。

六、避免前端样式错误
1. 只改样式时，必须修改工程根目录 static/（如 static/css、static/js），不要改 src/main/resources/static，也不要指望 WAR 内资源热更新。
2. 新增 CSS 类名要与现有命名风格一致，避免与已有类冲突；不要随意覆盖全局标签样式（如 body、table、button）。
3. 使用项目已有的 CSS 框架/变量（如有），不要引入新的 CDN 或 UI 库。
4. 布局改动要兼顾移动端：表格加 overflow-x:auto，按钮/输入框不要写死固定宽度导致小屏溢出。
5. 修改 Thymeleaf 中嵌入的 style 时，确保不破坏原有选择器；不要使用内联 style 覆盖全局样式，除非必要。
6. 图片/字体路径使用 @{...} 或相对 static 的正确路径，避免 404。
7. 改完前端后，列出受影响的页面路径，方便我逐一 F5 验证；并确认改动已落在根目录 templates/、static/。
